# 03 · “주요한 사실” 계층의 부재 — 핵심 결함

## 사용자 철학 vs 코드의 매핑표

| 사용자 철학 | 현재 아키텍처 매핑 | 실재 여부 |
|---|---|---|
| **T1 주요한 사실** (매 턴 무조건 주입) | (없음) | ❌ |
| T2 구체적 정보 (markdown LTM 저장) | `memory/**/*.md`, `StructuredMemoryWriter`, `ConversationArchiver` | ✅ |
| T3 탐색 능력 | `memory_search`, `memory_read`, `memory_list` 툴 | ✅ (단, 사용 시점 문제는 04 참조) |
| T4 LLM 추론 | system prompt + LLM | ✅ |

T1은 코드 어디에도 명시적인 자리가 없다. 가장 가까운 후보 두 개가 있지만 둘 다 T1을 만족하지 않는다.

### 후보 1 — `MEMORY.md`

`Geny/backend/service/memory/long_term.py`의 `MAIN_FILE = "MEMORY.md"`. `GenyMemoryRetriever`의 L2가 항상 로드한다(`retriever.py:307-329`).

문제:
- 무엇이 `MEMORY.md`로 들어가야 하는지 **자동 결정 규칙이 없다**.
- `LTM.append(text, heading=None)`가 호출되어야 들어가는데 — 이걸 호출하는 자동 경로는 사실상 없다(에이전트가 명시적으로 `memory_*` 툴 중 main에 쓰는 걸 호출해야 함).
- 인사이트 추출 경로(`GenyMemoryStrategy._save_insights` → `write_note`)는 **카테고리별 `<category>/<slug>.md`로만 떨어뜨리고** `MEMORY.md`는 손도 대지 않는다.
- 즉 “MEMORY.md = 주요한 사실” 의도는 있지만 **써넣는 사람이 없다.**

### 후보 2 — `Importance.CRITICAL`/`HIGH` 임포턴스 부스트

`Importance` enum은 `boost: float` 속성을 갖고(`geny-executor/src/geny_executor/memory/provider.py:103-110`), 키워드 검색 결과에 곱해진다(`retriever.py:399`).

문제:
- 부스트는 **검색 결과를 정렬할 때만 영향을 미친다.**
- 키워드 매칭 자체에서 떨어진 항목은 boost가 무한대여도 못 올라온다.
- 본 사례처럼 매칭이 0이면 boost는 무의미하다.

## 결과적으로 일어나는 일

1. `memory_distill` 또는 `GenyMemoryStrategy._save_insights`가 인사이트를 만들어 `insights/<slug>.md`에 저장한다. ← *저장은 정상*
2. 다음 세션이 시작된다. STM, 요약, MEMORY.md 모두 비어있다.
3. 사용자가 임의 질의를 던진다(예: `"뭐하고 있었어"`).
4. `GenyMemoryRetriever`가 6계층을 돌려도 어휘 일치가 없으면 0건.
5. system prompt에 메모리 섹션 자체가 사라진다.
6. 에이전트는 인사이트의 존재를 모른 채 응답.

이걸 사용자 철학에 맞춰 다시 보면:

> 주요한 사실은 반드시 기억해야 한다.

“반드시”의 보장이 코드 어디에도 없다. **검색이 잡는 데 성공해야만 나오는 “조건부 기억”**이다.

## 하드웨어 비유

CPU 비유로 표현하면 현재 구조는 다음과 같다.

```
            검색이 어휘 매칭에 성공한 경우에만   →  System Prompt에 들어감
LTM (Disk)  ──────────────────────────────────▶  L1 Cache (System Prompt)
            검색 실패 시 → 영원히 디스크에만
```

사용자 철학은 다음을 요구한다.

```
                Critical Facts (always-pinned)
LTM (Disk)  ──────────────────────────────▶  L1 Cache (System Prompt)
            ◀── promote on importance=critical/high ──
                Specific Notes (search-on-demand)
LTM (Disk)  ──────────────────────────────▶  Tool result (memory_search)
```

즉 **LTM 안에서도 “고정 캐시”와 “요청 시 로드”가 분리되어야 한다.**

## 도식적으로 어디에 무엇을 추가해야 하는가

```
memory/
├── critical/                        ← (NEW) T1 — 항상 주입
│   ├── user_preferences.md          (호칭, 톤, 좋아하는 것)
│   ├── persona_facts.md             (에이전트 이름, 역할)
│   └── relationships.md             (주요 인물)
│
├── conversations/                   ← T2 (현재) 그대로
├── dms/                             ← T2 (현재) 그대로
├── insights/                        ← T2 (현재) 그대로
├── topics/                          ← T2 (현재) 그대로
├── projects/                        ← T2 (현재) 그대로
└── MEMORY.md                        ← T1의 일부로 흡수 가능
```

그리고 두 종류의 promote 규칙이 필요하다.

1. **자동 prompt**: `Importance.CRITICAL` 인사이트는 저장 시 `critical/` 으로 함께(또는 단독으로) 떨어진다.
2. **명시적 promote tool**: 에이전트가 “이건 영구히 기억해야 함”을 판단했을 때 호출하는 `memory_pin` 같은 툴.

## 비슷한 시도가 코드에 있는가

있다. 그런데 미완성이다.

### `GenyMemoryStrategy._auto_promote` (executor)

`geny-executor/src/geny_executor/memory/strategy.py:435-446`:

```python
if importance in self._auto_promote and self._curated:
    try:
        self._curated.write_note(
            title=item.get("title", "Insight"),
            content=item.get("content", ""),
            category=requested_category,
            tags=item.get("tags", []) + ["auto-promoted"],
            importance=importance,
            source="promoted",
        )
    except Exception:
        pass
```

CRITICAL/HIGH 인사이트를 **CuratedKnowledgeManager로 복제**한다. 하지만:
- 큐레이티드도 검색 기반 회수다(`curated.inject_context(query, ...)`).
- 즉 promote가 일어나도 **여전히 어휘 매칭에 묶여 있다.**

### `MemoryDescriptor.compatibility_check` (executor)

`geny-executor/src/geny_executor/memory/provider.py:560-585`. 임베딩 호환성 체크용으로, 본 주제와 무관.

### Provider Protocol의 `promote()`

`provider.py:749`. scope 사이의 ref 이동 — 현재 어느 provider도 “critical 계층으로 영구 고정”을 의미하는 promote를 구현하지 않는다. 단순 scope rename 수준.

## 정리

- 코드의 **모든 추출 경로**는 “쿼리 텍스트와의 매칭”에 의존한다.
- T1 “항상 주입” 계층이 명시되지 않았기에, 사용자가 보기엔 **저장된 것이 안 떠오른 것처럼** 보인다.
- 후보 메커니즘(MEMORY.md, importance boost, auto_promote)이 있으나 **모두 검색 매칭이 일어난 후의 가산 효과**에 그친다.

다음 문서(`04_탐색능력_무력화.md`)에서는 “그래도 에이전트가 능동적으로 `memory_search`를 부르면 되지 않냐”에 대한 검증을 한다.
