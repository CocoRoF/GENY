# 04 · 탐색 능력은 있지만 작동하지 않는 이유

사용자 철학 T3: “Agent는 환경 속 탐색 능력을 갖추고 있는 상태”.

코드 측면에서 “탐색 능력”은 다음 툴들이다(`Geny/backend/tools/built_in/memory_tools.py`).

| 툴 이름 | 호출 시그니처 | 기능 |
|---|---|---|
| `memory_search` | `(session_id, query, max_results=10, counterpart?, kinds?)` | `manager.search(query)`로 LTM+STM 키워드+백링크 회수 |
| `memory_read` | `(session_id, filename)` | 단일 노트 본문 읽기 |
| `memory_list` | `(session_id, category?, tag?)` | 노트 목록 |
| `memory_write` | `(session_id, title, content, category, tags, importance, source, links_to)` | 새 노트 저장 |
| `memory_update` | `(session_id, filename, body?, tags?, importance?)` | 노트 수정 |
| `memory_delete` | `(session_id, filename)` | 노트 삭제 |
| `memory_link` | `(session_id, source, target)` | 위키링크 |
| `memory_status` | `(session_id, ...)` | 통계 |
| `memory_distill` | `(session_id, counterpart?)` | LLM 기반 인사이트 distill |

추가로 `memory_inspect_tools.py`에는 `MemoryEventTool`, `MemoryWithTool`, `MemoryArtifactTool` 등 read-only 진단 툴이 있다.

즉 **툴은 충분히 갖춰져 있다.** 그런데 스크린샷의 케이스에서 에이전트는 이 툴 중 어느 것도 부르지 않았다. 왜인가?

## 문제 1 — 시스템 프롬프트가 능동적 탐색을 명령하지 않는다

`geny-executor/src/geny_executor/memory/presets.py:344-352`(VTuber 기본 프롬프트):

```python
_DEFAULT_VTUBER_PROMPT = """\
You are a friendly AI VTuber assistant. Engage in natural conversation
while being helpful and knowledgeable.

When the user asks a complex task that requires tools or multi-step work,
indicate that you will delegate it.

Keep responses conversational and natural."""
```

“복잡한 작업이면 위임” 정도만 있고, **“대화를 시작할 때 메모리를 먼저 검색하라”는 지침은 없다.** 워커 프롬프트(`_DEFAULT_WORKER_PROMPT`)도 마찬가지로 메모리에 대한 언급이 없다.

`Geny/backend/service/persona/blocks_resolver.py`도 페르소나 블록 + 시간 + memory_context만 붙이지, 툴 사용 가이드를 박지 않는다.

결과적으로 LLM이 “주인님이라고 부른다는 사실” 같은 메타 정보를 부를 동기가 없다.
사용자가 명시적으로 “내 호칭 기억 안 나?” 라고 물어야 비로소 search를 시도할 수 있는데, 본 케이스에선 그 두 번째 발화에서도 search 콜이 안 보인다(에이전트가 “기록을 보니까 …” 라고 말하지만 실제 툴 호출 없이 LLM이 자기 직전 컨텍스트(=빈 메모리)만 보고 한 말일 가능성이 매우 높다).

## 문제 2 — search 자체가 한국어/영어 혼합 케이스에서 신뢰할 수 없다

설사 에이전트가 `memory_search(query="...")`를 불러도, `manager.search()` → `_ltm.search()`의 키워드 매칭 로직(`02_주인님_인사이트_실패경로.md`에서 본 것)은 동일하다.

다국어 + 자연어 질문이 영어 인사이트 본문과 안 맞으면 결과가 비어 나온다. 즉 **탐색 능력의 도구는 있지만 도구 자체의 회수율이 낮다.**

벡터 검색이 활성화되어 있을 때 에이전트가 `memory_search`를 부르면 `manager.search()`는 키워드 모드만 쓴다(`manager.py:991-1022`). 벡터 검색은 `build_memory_context_async()` 안에서만 이용 가능했고, 이 함수도 deprecated. 즉 **에이전트가 직접 호출하는 search는 벡터 fallback조차 없다.**

## 문제 3 — slim_mode가 켜졌을 때조차 “탐색”으로 흐르지 않는다

slim_mode를 켜면 retrieve 결과가 vault_map(목차 ~500자)로 줄어든다. 의도는 “목차만 보여주고 본문은 에이전트가 툴로 가져가라”다(Memory v2 PR 9/10).

문제:
- vault_map은 `index.py:render_vault_map()`이 만드는 카테고리/태그/파일명 인덱스다. 인사이트의 *본문*도 *제목*도 아닌 메타데이터다.
- 사용자 발화가 “호칭” 관련이면 vault_map의 “insights/User prefers to be addressed as 주인님”이 보이고 에이전트가 그 파일을 `memory_read`할 수 있겠지만, 본 케이스 첫 발화 “뭐하고 있었어”는 그 단서를 *보이지 않게* 한다.
- 게다가 slim_mode는 기본 OFF이므로 본 사례에서도 작동하지 않았다.

## 문제 4 — 탐색을 부추길 정보 자체가 빠져 있다

다른 코드베이스(예: Anthropic의 [skill] 스타일)에서는 system prompt에 “현재 환경에 무엇이 있는지” 인덱스를 박아두고, 에이전트가 그걸 보고 탐색을 시작한다. Geny에는 그 게이트웨이가 거의 없다.

- `MemoryContextBlock`은 `state.metadata["memory_context"]`(검색이 모은 텍스트)만 출력 — 검색이 비면 빈칸.
- 페르소나 블록은 정적 텍스트.
- 툴 카탈로그(이름/설명)는 LLM에 전달되지만, **툴이 보호하는 자원의 “지도”는 없다.** “memory_search라는 툴이 있다”는 것만 알 뿐 “memory에 무엇이 들어있을 수 있는지”는 모른다.

T1(주요한 사실 자동 주입) 부재가 여기서도 영향을 준다. 만약 “이 사용자의 호칭 선호는 ‘주인님’”이 항상 system prompt에 있었다면, LLM은 굳이 search를 부를 필요도 없이 정답을 안다. 즉 **T1이 있으면 T3가 부족해도 보완된다. 반대로 T1이 없으면 T3에 모든 부담이 가는데, T3 자체가 한국어 키워드 매칭 한계로 회수율이 낮다.**

## 정리

- 툴 자체는 풍부하다(9개+).
- 그러나 (a) 에이전트가 부를 동기가 약하고, (b) 부르더라도 키워드 검색이 다국어 케이스에서 무력하며, (c) slim_mode(목차 인젝션)는 기본 꺼져있다.
- T1이 부재하기 때문에 T3에 회수 책임이 전가되는데, T3의 회수율도 낮아 결과적으로 **에이전트는 안 보고 모른다**.
